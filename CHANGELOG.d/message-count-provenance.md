Added a counting-provenance registry (`contextual_orchestrator/token_counting.py`) that binds exact chat-message token counting to a citable official source and its exact declared model scope, per issue #1157. `COUNTING_PROVENANCE_REGISTRY` records, per exact model identifier, the `tokenizer`, `framing_source` (currently the OpenAI Cookbook's "How to count tokens with tiktoken", fetched live 2026-09-14, scoped to exactly the seven dated model identifiers it names), `supported_fields` (`role`/`content`/`name`, string-valued only), and `unsupported_fields` (tools, tool/function calls, non-text content parts, instructions, prior response/conversation references). `NativeExactTokenCounter.describe_messages`/`count_messages` now return an exact, provenance-bound count only inside that scope; any unsupported field, non-text value, or out-of-scope model keeps raising `TokenCountUnavailable`, naming the offending field. Added `describe_message_count()` as a counter-agnostic convenience returning a `MessageCountResult` with `count_source`. `chat_completion_response()` gained an optional `prompt_count_source` field (populated by `contextual_orchestrator.server._prompt_count_source`) that is present only when the served request's exact prompt-message count was obtained from this registry, and omitted — never fabricated — otherwise. Tool/modality/multi-turn-context token accounting remains open per #1157; this is the smallest honest step, not a full resolution.

Second half of #1157: added `token_counting.shared_context_output_budget(agent, messages, requested_output_tokens, *, counter, tools=None)`, an honest shared-context output-budget decision that returns a `SharedContextBudget` (`context_window`, `prompt_tokens`, `remaining`, `output_ceiling`, `exceeds_remaining`) only when the agent's `context_window`, its published `max_output_tokens`, and an exact registry-verified prompt count are all authoritative — otherwise `None`, never an estimate or a fixed ratio. `ModelClient.chat()` applies the decision at the same site as the existing catalog output-ceiling clamp, before the provider call: with no explicit caller/client output budget it sends `min(max_output_tokens, remaining)`; when the caller's explicit budget (or a `remaining < 1` shared-context shortfall) would exceed the remaining shared capacity, it raises `ProviderRequestTooLargeError` naming `context_window`, `prompt_tokens`, and the requested budget instead of silently truncating. `ModelClient` gained an optional `token_counter` constructor argument (the default `TaskOrchestrator` wires its own counter into its default client) and `take_shared_context_budget()`, mirroring `take_usage()`. The served `/v1/chat/completions` response now carries an optional `shared_context_budget` evidence object (`context_window`/`prompt_tokens`/`output_ceiling`/`source: "exact"`) next to `prompt_count_source`, populated by `server._take_shared_context_budget()`, and omitted when no decision was made.

Follow-up closing the streaming/passthrough gap left above: `ModelClient._stream_send` now applies the identical decision at the exact site its own plain catalog clamp already ran, before any provider bytes are sent for that attempt — same `min(max_output_tokens, remaining)` default and the same `ProviderRequestTooLargeError` on an over-remaining explicit budget or `remaining < 1`. The true streaming `/v1/chat/completions` route (`server._stream_route_completion`) already flushes SSE response headers and its first (`role: assistant`) frame before the provider call is attempted, so a rejection now necessarily surfaces as a terminal error frame rather than a pre-request HTTP error — the existing `ProviderUpstreamError` handling there already covers `ProviderRequestTooLargeError` (it is one), so no new frame-shape work was needed for the error path. The success terminal ("stop") frame now carries the same `shared_context_budget` evidence object as the non-streaming response (same field name, same shape) whenever `ModelClient.take_shared_context_budget()` returns one, via `server._take_shared_context_budget()` reused verbatim; it is omitted otherwise. `ModelClient._proxy_send` (the passthrough/local-proxy transport behind `proxy_send`/`proxy_send_once`/`probe_structured_chat`, used by the server's single-agent tool-loop passthrough) gained the same decision for the `chat/completions` endpoint, reading the caller's own `max_tokens` from the untouched passthrough body before the existing local-provider default-cap injection runs (so a gateway-injected local default is never mistaken for a caller's own explicit budget) — `shared_context_output_budget` already returns `None` for any body shape `describe_message_count` cannot account for (a Responses-shaped `input` body, `tools`, non-text content, an out-of-scope model), so no estimate is ever forced onto a passthrough request the registry cannot honestly count; that response body is deliberately left as the verbatim provider shape (no evidence field is added to it), consistent with this transport's existing "full provider response shape survives verbatim" contract. The `responses`-endpoint and batch-upload send paths are unchanged and still use only the plain catalog clamp — out of scope for this follow-up, since the former does not reduce to exact chat-message accounting and the latter is a separate async transport.
