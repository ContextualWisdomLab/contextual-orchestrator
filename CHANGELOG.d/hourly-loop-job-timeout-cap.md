Bounded the hourly OpenCode maintenance loop's `loop` job with an explicit `timeout-minutes: 300` (5h) instead of relying on GitHub Actions' implicit 360-minute per-job cap. The job's `concurrency: { group: opencode-hourly-loop, cancel-in-progress: false }` means a single wedged run could otherwise occupy the group for up to 6 hours, silently superseding every hourly trigger queued behind it. 300 minutes stays comfortably above this loop's expected 2h+ per-model gateway/inference runs while leaving real margin under the platform's hard 360-minute ceiling.
